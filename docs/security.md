# Безопасность

## Угрозы и меры

| Угроза | Мера |
|---|---|
| Перехват трафика | TLS 1.2+ по умолчанию, можно требовать 1.3; HSTS |
| Посторонние клиенты | API-ключи; опционально mTLS и привязка ключа к сертификату |
| Утечка конфигурации | Хранятся только SHA-256 хеши ключей |
| Подбор ключей, флуд | Лимит по IP до аутентификации и по ключу после, IPv6 по сети /64 |
| Превышение прав | Роли `reader` и `writer`, проверка до чтения тела |
| Некорректные данные | Проверки в спецификации, домене и БД |
| SQL-инъекции | Только статические параметризованные запросы |
| Исчерпание ресурсов | Таймауты, лимиты размера, `statement_timeout`, ограниченная память лимитера и метрик |
| Потерянные обновления | `If-Match` → `412`; чужая запись без версии → `428` |
| Утечка внутренних деталей | Нейтральные ошибки, подробности в логе по `request_id` |
| Подделка IP | `X-Forwarded-For` учитывается только от `HTTP_TRUSTED_PROXIES` |
| Взлом контейнера | Distroless, non-root, read-only FS, `cap_drop: ALL`, лимиты памяти и процессов |
| Взлом сервиса | Роль в БД без прав на схему и на запись в историю |
| Отсутствие аудита | Автор и история изменений записываются сервером, access-лог с ключом |

## Аутентификация

Сервер ищет запись по SHA-256 от ключа, а не сравнивает ключи, поэтому время ответа не
выдаёт, насколько ключ похож на настоящий. Для случайных ключей на 256 бит быстрого хеша
без соли достаточно, в отличие от паролей.

**Почему не OAuth 2.0:** клиенты сервиса это системы партнёров, а не люди, а OAuth требует
отдельного сервера авторизации. JWT можно добавить реализацией интерфейса
`auth.Authenticator`, не меняя HTTP-слой.

**Смена ключа:** на один `id` можно выдать несколько ключей с одной ролью. При
`AUTH_API_KEYS_FILE` сигнал `SIGHUP` перечитывает файл, а битый файл оставляет прежние ключи.

## TLS и mTLS

- Без сертификатов сервис не стартует, пока явно не задано `TLS_ENABLED=false`.
- `TLS_CLIENT_CA_FILE` включает обязательную проверку клиентского сертификата.
- `AUTH_BIND_CLIENT_CERT=true` требует, чтобы Common Name сертификата совпадал с `id` ключа:
  утекший ключ бесполезен без закрытого ключа владельца.
- `SIGHUP` перечитывает сертификат, при ошибке остаётся прежний.
- `devcerts` создаёт сертификаты только для разработки.

## Достоверность данных

Запись общая: любой `writer` может её отозвать или сменить `red` на `green`. `If-Match`
защищает от случайного затирания, а история показывает автора изменения, но намеренную
подмену это не предотвращает. Поэтому роль `writer` стоит выдавать только доверенным
организациям. Как устранить риск полностью, описано в
[решении 7](decisions.md#7-одна-общая-запись-на-md5).

Метка `tlp` не ограничивает доступ: запись получит любой ключ с правом чтения, а соблюдать
метку должен получатель.

## Служебный порт

`/healthz`, `/readyz` и `/metrics` работают на отдельном порту без аутентификации. В compose
он открыт только на `127.0.0.1`, в Kubernetes должен быть доступен лишь kubelet и Prometheus.
Docker проверяет `/healthz`, потому что перезапуск сервиса не исправит сбой БД.

## Для продакшена

1. Сертификаты из корпоративной PKI с автоматической ротацией.
2. Секреты через `*_FILE`, а не в переменных окружения.
3. Свои пароли и сертификаты для ролей БД, `sslmode=verify-full`.
4. При нескольких репликах rate-limit на API-gateway или в общем хранилище.
5. Образы, закреплённые по digest, и регулярное сканирование.
6. Сбор логов и оповещения о `5xx`, `threat_exchange_auth_failures_total` и
   `threat_exchange_rate_limited_total`.
