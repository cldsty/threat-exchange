# Безопасность

## Модель угроз (кратко)

| Угроза | Мера |
|---|---|
| Перехват и подмена трафика | TLS 1.2+ по умолчанию (можно требовать 1.3); современные наборы шифров Go, включая гибридный постквантовый обмен ключами `X25519MLKEM768`; HSTS. |
| Подключение посторонних систем | API-ключи; опционально mTLS — без сертификата доверенного CA соединение не устанавливается; опционально привязка ключа к сертификату владельца. |
| Утечка ключей из конфигурации или БД | Хранятся только SHA-256 хеши ключей; сами ключи — 256 бит случайности с префиксом `tx_` (их находят сканеры секретов). |
| Подбор ключей, флуд | Rate-limit по IP до аутентификации и по ключу после, IPv6 — по сети /64; `429` с `Retry-After`; метрики отказов. Стоимость проверки лимита не зависит от числа клиентов. |
| Превышение прав | Роли `reader`/`writer`; проверка до чтения тела запроса. |
| Некорректные или вредоносные данные | Валидация по спецификации, в домене и `CHECK`-ограничения в БД; лишние поля, данные после JSON и другие типы содержимого отклоняются; в именах запрещены невидимые символы и смена направления текста. |
| SQL-инъекции | Только статические параметризованные запросы pgx. |
| Исчерпание ресурсов (slowloris, большие тела) | `ReadHeaderTimeout`, таймауты чтения/записи/простоя, лимит заголовков и тела, дедлайн обработки, `statement_timeout` в PostgreSQL, ограничение памяти rate-limiter; метод запроса не попадает в метки метрик как есть. |
| Потерянные обновления | Оптимистичная блокировка: `ETag` + `If-Match` → `412`; замена чужой записи без версии → `428`. |
| Затирание или подмена данных партнёром | История всех версий в `threat_history`; риск подмены описан ниже. |
| Утечка внутренних деталей | Нейтральные сообщения об ошибках; детали только в логе, все записи которого содержат `request_id`; пароль из `DB_URL` не попадает в ошибки. |
| Подделка IP через `X-Forwarded-For` | Заголовок учитывается только от доверенных прокси (`HTTP_TRUSTED_PROXIES`), берётся крайний правый недоверенный адрес. |
| Компрометация контейнера | Distroless-образ без shell, пользователь не root, read-only FS, `cap_drop: ALL`, `no-new-privileges`, лимиты памяти и процессов; в БД сервис работает под ролью без прав на схему и на запись в историю. |
| Отсутствие аудита | `created_by`/`updated_by` из аутентифицированного ключа; структурированный access-лог с principal. |

## Аутентификация

```
X-API-Key: tx_…    →  sha256(key)  →  поиск по хешу  →  Principal{ID, Role}
```

Поиск идёт по хешу, а не сравнением ключей, поэтому время ответа не выдаёт,
насколько ключ «похож» на настоящий. Для ключей с энтропией 256 бит быстрый
хеш без соли достаточен (в отличие от паролей пользователей).

Почему не JWT/OAuth 2.0: клиенты сервиса — системы-партнёры, а не люди с
логином; OAuth требует отдельного сервера авторизации. Этот же подход
использует Kaspersky Threat Intelligence Portal (`x-api-key`). Проверка
вынесена за интерфейс `auth.Authenticator`, так что JWT можно добавить
реализацией одного интерфейса.

Ключи можно менять без перезапуска: при `AUTH_API_KEYS_FILE` сигнал `SIGHUP`
перечитывает файл, а битый файл оставляет прежние ключи. На один `id` можно выдать
несколько ключей с одной ролью, чтобы заменить ключ без простоя.

## TLS и mTLS

- Без сертификатов сервис не стартует, пока явно не задано `TLS_ENABLED=false`
  (только за TLS-терминирующим прокси, сервис пишет предупреждение в лог).
- `TLS_CLIENT_CA_FILE` включает обязательную проверку клиентского сертификата.
- `AUTH_BIND_CLIENT_CERT=true` дополнительно требует, чтобы Common Name сертификата
  совпадал с `id` ключа: утекший ключ бесполезен без закрытого ключа его владельца.
- Сертификат можно заменить на диске и отправить `SIGHUP` — новые соединения
  получат новый сертификат без перезапуска. Если новый файл битый, остаётся
  прежний сертификат.
- `devcerts` генерирует CA, серверный и клиентский сертификаты (ECDSA P-256)
  **только для разработки**.

## Достоверность данных

Запись об угрозе общая: её может изменить любой `writer`, в том числе отозвать или
сменить `red` на `green`. Требование `If-Match` защищает от случайного затирания,
а история показывает, кто и что изменил, но ни то ни другое не предотвращает
намеренную подмену. Поэтому роль `writer` стоит выдавать только организациям,
которым доверяют, и следить за историей. Как устранить риск полностью, описано в
[решении 13](decisions.md#13-одна-общая-запись-на-md5-и-история-изменений).

Метка `tlp` не является контролем доступа: сервер отдаёт запись любому ключу с
правом чтения, а соблюдение метки остаётся обязанностью получателя.

## Служебный порт

`/healthz`, `/readyz`, `/metrics` вынесены на отдельный порт без
аутентификации. В compose он опубликован только на `127.0.0.1`; в
Kubernetes он должен быть доступен лишь kubelet и Prometheus. Проверка живости
контейнера использует `/healthz`: перезапуск сервиса не исправит сбой БД.

## Рекомендации для продакшена

1. Сертификаты из корпоративной PKI, автоматическая ротация (cert-manager) + SIGHUP.
2. Секреты через `*_FILE` (Docker/Kubernetes secrets, Vault), а не в переменных.
3. Роли PostgreSQL и TLS до БД, как в compose: отдельная роль для миграций (DDL)
   и `threats_app` для сервиса, `sslmode=verify-full`, но с паролями из секретов
   и сертификатами из PKI.
4. При нескольких репликах — rate-limit на API-gateway или в общем хранилище.
5. Закрепить образы по digest, регулярно сканировать (в CI — Trivy и govulncheck).
6. Сбор логов (ELK/Loki) и алерты по метрикам `threat_exchange_auth_failures_total`,
   `threat_exchange_rate_limited_total`, доле ответов 5xx.
