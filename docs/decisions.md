# Принятые решения

Короткие записи в духе ADR: что решили и почему.

## 1. Модель угрозы ориентирована на Kaspersky OpenTIP

- **`zone`** (`red/orange/yellow/green/grey`) — как цветовые зоны Kaspersky
  Threat Intelligence Portal. Отвечает на вопрос «вредоносный ли объект».
  По умолчанию `grey` — «данных недостаточно».
- **`severity`** — отдельный вопрос «насколько опасно». Значение `unknown`
  честно означает «не оценено» вместо угаданного уровня. Чтобы данные не
  противоречили друг другу, для `green`/`grey` допустимо только `unknown`.
- **`types`** — массив из словаря, построенного по части `Behaviour` в именах
  Kaspersky (`Trojan.Win32…`, `Backdoor.Linux…`). Массив, потому что в обмене
  между организациями один образец часто описывают несколькими категориями;
  фиксированный словарь — чтобы не было разнобоя `Trojan`/`trojan`/`trojan-horse`;
  `other` закрывает редкие случаи.
- **`first_seen_at`/`last_seen_at`, `file_size`, `sha1`/`sha256`** — есть в
  OpenTIP и полезны для сопоставления данных из разных источников.
- **`revoked`** — ложные срабатывания отзывают, а не удаляют; прежние версии
  записи остаются в истории (см. решение 13).
- **`tlp`** — метка распространения TLP 2.0, стандарт для обмена данными об
  угрозах. По умолчанию `amber`: если автор ничего не указал, безопаснее считать,
  что данные нельзя распространять свободно. Сервер хранит и передаёт метку, но
  не ограничивает по ней чтение: для этого ключи нужно привязать к организациям
  и уровням доступа.
- **`confidence`** — уверенность автора в оценке (0–100, как в STIX 2.1): `zone`
  и `severity` отвечают на вопрос «что это», но не «насколько автор уверен».
- **`created_by`/`updated_by`** заполняет сервер по API-ключу — аудит,
  который клиент не может подделать.
- **`platform` не вводилась**: платформа уже есть в имени угрозы — два места
  для одного факта ведут к противоречиям.
- **Имя не проверяется по формату Kaspersky**: в обмене встречаются имена других
  вендоров; запрещены только пробелы по краям и управляющие символы.

## 2. Совместимость с исходным контрактом

Обязательными остались только `md5` и `name`, как в задании, а новые поля
получают значения по умолчанию. Защита добавляет к контракту новые требования:
TLS, заголовок `X-API-Key` и запрет лишних полей в теле запроса. Клиент с данными
только из исходной спецификации должен передать ключ, остальное в его запросах
менять не нужно.

## 3. `PUT` — полная замена, MD5 из пути

По семантике HTTP и описанию в задании («заменяет информацию»). MD5 в теле
`PUT` отклоняется (`additionalProperties: false`), чтобы не было двусмысленности
«какой MD5 правильный».

## 4. Оптимистичная блокировка через ETag/If-Match

Защищает от «потерянного обновления», когда два аналитика правят одну запись.
`If-Match` принимает и список версий, как требует RFC 9110. Без него можно менять
только собственную запись, см. решение 13.

Значение `ETag` берётся из столбца `version`: `UPDATE … WHERE version = $v`
атомарно проверяет его при записи. В теле ответа версии нет: она дублировала бы
заголовок, а двум источникам одного значения незачем существовать.

## 5. Спецификация — единственный источник правды

`oapi-codegen` генерирует strict-интерфейс: обработчик может вернуть только
объявленные в спецификации ответы, иначе код не скомпилируется. Тот же файл,
встроенный в бинарник, использует валидатор kin-openapi. CI проверяет, что
сгенерированный код не устарел (`make check-generate`).

## 6. pgx и рукописный SQL вместо ORM

Запросов всего четыре, они статические и параметризованные. ORM добавила бы
сложность без пользы, а генератор запросов вроде `sqlc` окупается при большем их
числе. Корректность SQL проверяют интеграционные тесты на реальном PostgreSQL,
включая ограничения схемы. Если запросов станет много, перейти на `sqlc` можно
заменой одного файла.

## 7. Миграции goose, встроенные в бинарник

Схема версионируется вместе с кодом, отдельный инструмент в образе не нужен.
Advisory lock делает запуск безопасным для нескольких реплик. В compose
миграции — отдельный одноразовый сервис, а не шаг старта приложения.

## 8. Текстовые столбцы с `CHECK` вместо `ENUM` PostgreSQL

Значения перечислений проще менять миграцией (`ALTER TABLE … CHECK`), чем
`ALTER TYPE`; при этом БД по-прежнему не примет неизвестное значение.

## 9. API-ключи, а не JWT/OAuth

См. [security.md](security.md#аутентификация).

## 10. Интеграционные тесты на отдельных временных базах

Каждый тест создаёт базу `tx_test_<random>`, мигрирует и удаляет её. Тесты
параллельны и независимы, а для запуска нужен только адрес PostgreSQL
(`TEST_DB_URL`): в CI — service container, локально — `docker compose up db`.
Альтернатива — testcontainers-go — даёт то же, но тянет Docker SDK в
зависимости проекта.

## 11. Конфигурация из окружения, секреты из файлов

12-factor: один образ для всех сред. `*_FILE` позволяет не держать секреты в
переменных окружения. Конфигурация валидируется целиком при старте, все
ошибки выводятся сразу.

## 12. Инструменты разработки в отдельном модуле

`tools/go.mod` фиксирует версию oapi-codegen (`go tool -modfile=tools/go.mod`)
и не засоряет зависимости основного модуля.

## 13. Одна общая запись на MD5 и история изменений

В сервисе обмена данные об одной угрозе могут появиться у нескольких организаций.
В задании MD5 уникален, а `PUT` заменяет данные, поэтому выбрана общая запись:

- менять её может любой `writer`, а не только автор: иначе вторая организация не
  смогла бы передать свои данные (`409` на `POST` и `403` на `PUT`);
- запись, которую последним менял другой ключ, нельзя заменить без конкретной
  версии в `If-Match` (`428`), поэтому организация обязана сначала прочитать чужие
  данные. Значение `*` такой проверкой не считается;
- все версии сохраняются в `threat_history`, поэтому данные не теряются при замене.

Историю заполняет триггер, а не код сервиса: она останется полной и при изменении
в обход сервиса и не сможет разойтись с основной таблицей. Отдельного эндпоинта
нет: в задании его не просили, а для аудита хватает таблицы.

**Что остаётся нерешённым.** Партнёр может сменить `red` на `green`, и читатели
увидят новое значение. История покажет, кто это сделал, но не предотвратит подмену.

**Следующий шаг** — отдельный отчёт от каждой организации на один MD5, а `GET`
возвращает сводку по ним и список отчётов. Это закрывает риск подмены, но меняет
смысл контракта (`409` перестаёт означать «MD5 уже есть») и требует правил слияния
при разногласиях, поэтому в рамках задания не реализовано.

## 14. Уникальность только у SHA-256

У одного файла один MD5, поэтому два MD5 с одним SHA-256 означают ошибку в данных:
такая запись отклоняется (`409`). Для SHA-1 уникальности нет: известны разные файлы
с одинаковым SHA-1 (SHAttered), и такое ограничение отклоняло бы настоящие данные.
Коллизии MD5 тоже существуют, но ключ по MD5 задан контрактом: два файла с одним
MD5 попадут в одну запись. Для этого в записи и есть `sha256`.

## 15. Роль сервиса в базе данных без права менять схему

В compose миграции работают под владельцем схемы, а сервис — под ролью
`threats_app` с правами `SELECT, INSERT, UPDATE` на `threats` и `SELECT` на
`threat_history`. Взломанный сервис не сможет ни удалить таблицу, ни переписать
историю. Права выдаёт миграция, если такая роль есть: тестам и другим развёртываниям
она не нужна.

## 16. Демонстрация: OpenAPI, Swagger только для чтения и сценарий

Основа документации — спецификация OpenAPI, примеры `curl` дополняют её в README.
Swagger UI вынесен в отдельный контейнер: сервису не нужны дополнительные файлы и
исключения из защиты. Отправка запросов из браузера отключена, потому что для неё
API пришлось бы разрешить CORS, а браузеру довериться dev-CA. Сценарий
`deploy/demo/demo.sh` показывает работу двух организаций одной командой на любой
системе и проверяет каждый ответ, поэтому он же служит дымовым тестом в CI.
